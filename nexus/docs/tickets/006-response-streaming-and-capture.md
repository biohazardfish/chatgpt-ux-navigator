# Ticket 006 - Response Streaming and Capture (Session Run Transcripts)

## Title

Response Streaming and Capture (Session Run Transcripts)

## Goal

Extend the server client so Nexus can **capture and persist raw session outputs** (“transcripts”) for each execution run (MVP: **buffered JSON mode only**, no Nexus-side SSE parsing), while keeping these transcripts clearly separated from interpreted reports and persistent project state.

For canonical terminology, see the glossary in `nexus/docs/006-session-orchestration.md#glossary`.

This ticket introduces the concept of a **session run** as an execution artifact.

---

## Context

From earlier tickets:

- **Persistent project state** (projects, plans, tasks, decisions) is curated and long-lived.
- **Session outputs** are ephemeral execution results.
- However, for debugging, transparency, and governance confidence, Nexus should retain **raw outputs per run** for inspection.

The local server (as used by Nexus in MVP):
- Returns a **single buffered JSON response** containing the full response text
- Does **not** require Nexus-side streaming/SSE parsing
- Does not provide structured metadata beyond the buffered payload

This ticket captures that text safely and predictably.

### MVP capture contract

- Per `nexus/docs/006-session-orchestration.md#mvp-decisions-resolved`, capture is **buffered JSON only**; anything referencing streaming must carry a **Future work** label.
- This ticket never adds a TUI streaming display in MVP; Nexus persists the buffered payload for later inspection instead.
- Any other doc that references run capture should cite this section or the canonical decisions rather than restating the policy.

---

## Definitions

### Session Run
A **session run** is a single execution of a prompt against the server.

A run is identified by:
- `runId` (generated by Nexus)
- `responseId` (channel sent to server, e.g. `planner`, `reviewer-1`)
- Timestamp
- Prompt text
- Raw response text

MVP identifier mapping:
- `responseId` (this doc) == server routing `clientId` == role name

Runs are **not part of project intent** and are not used as memory.

---

## Storage location

All run artifacts live under:

```
<stateDir>/runs/
```

### Directory structure

```
runs/
  <project-id>/
    <run-id>/
      meta.json
      prompt.txt
      response.txt
```

Example:
```
runs/nexus-mvp/20260201T131200Z-planner/
  meta.json
  prompt.txt
  response.txt
```

---

## Run metadata

### `meta.json`
```json
{
  "runId": "20260201T131200Z-planner",
  "projectId": "nexus-mvp",
  "taskId": "T-003",
  "role": "planner",
  "responseId": "planner",
  "startedAt": "2026-02-01T13:12:00Z",
  "completedAt": "2026-02-01T13:12:47Z",
  "status": "success"
}
```

Notes:
- `status` here is **transport-level** (`success | error | timeout`)
- This is distinct from **report status** (`success | partial | blocked`)

---

## Requirements

### Functional
1. Generate a unique `runId` for every server execution.
2. Persist:
   - Prompt text (`prompt.txt`)
   - Full raw response text (`response.txt`)
   - Minimal metadata (`meta.json`)
3. Support **buffered JSON responses** (entire response returned at once; MVP does not parse SSE/streaming — see `nexus/docs/006-session-orchestration.md#mvp-decisions-resolved`).
4. **Future work:** support **streaming responses** (SSE / `ReadableStream`) and streaming parsing on the Nexus side.
5. Ensure runs are written **after completion** (no partial corruption).
6. Never mix run data with project state or reports.

### Non-functional
- (Future work) Streaming support may be basic (append chunks to memory, then flush to disk).
- No real-time TUI streaming display yet (later ticket; keep labeled **Future work** per `nexus/docs/006-session-orchestration.md#mvp-decisions-resolved`).
- No retry logic yet.

---

## Out of scope
- Parsing reports from responses
- Attaching runs to tasks automatically (only metadata link)
- Cleanup / retention policies
- UI for viewing transcripts

## API design (internal)

Introduce a run executor:

```ts
interface SessionRunParams {
  projectId: string
  taskId?: string
  role: Role
  responseId: string
  prompt: string
}

interface SessionRunResult {
  runId: string
  responseText: string
}
```

```ts
async function executeSessionRun(
  params: SessionRunParams
): Promise<SessionRunResult>
```

This function:
- Wraps `serverClient.postPrompt`
- Handles capture + persistence
- Returns response text for downstream parsing

## Streaming behavior (Future work)

> **Future work note:** This entire section describes non-MVP behavior. MVP capture is buffered JSON mode only (`nexus/docs/006-session-orchestration.md#mvp-decisions-resolved`).

### Detection
- If `fetch` response has `body` as a `ReadableStream`, read chunks
- Else, fall back to `await response.text()`

### Future work handling
- Accumulate chunks in memory
- On completion:
  - Write `response.txt`
  - Update `meta.json`
- On error:
  - Write `meta.json` with `status: error`
  - Do **not** write partial `response.txt` unless explicitly decided (prefer atomic)

---

## Error handling

If execution fails:
- Capture:
  - Error message
  - Timestamp
- Persist `meta.json` with:
  ```json
  {
    "status": "error",
    "error": "Timeout while waiting for response"
  }
  ```
- Re-throw error so orchestration layer can react

## Path safety

- All writes must use `resolveInsideRoot(stateDir, ...)`
- No dynamic paths outside `<stateDir>/runs`

### New files
```

```

### Responsibilities
- `runExecutor.ts`
  - Generate runId
  - Call server client
  - Coordinate capture lifecycle
- `runs.ts`
  - Create run directory
  - Write `meta.json`, `prompt.txt`, `response.txt`
  - Update metadata safely

## Implementation steps

1. **Run ID generation**
   - Format: `<UTC timestamp>-<role>`
   - Example: `20260201T131200Z-planner`
   - Ensure filesystem-safe

2. **Run directory creation**
   - `<runsDir>/<projectId>/<runId>/`
   - Create directories atomically

3. **Persist prompt**
   - Write `prompt.txt` immediately after directory creation

4. **Execute server request**
   - Use client from ticket 005
   - Capture start + end time

5. **Persist response**
   - Write full `response.txt` on success

6. **Persist metadata**
   - Write `meta.json` last
   - Include status + timestamps
