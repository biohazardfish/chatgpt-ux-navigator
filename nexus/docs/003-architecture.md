# Docs 003 - Architecture

This document describes the high-level architecture of Nexus and how it interacts with the existing system components.

The goal of this architecture is to provide **clear separation of responsibilities**, predictable behavior, and strong governance over AI-driven work.

---

## High-Level Overview

Nexus is a **control-plane application** that orchestrates AI work but does not execute that work itself.

At a high level, the system consists of four major components:

1. User (Operator)
2. Nexus (TUI application)
3. Local Server
4. ChatGPT Sessions (via Browser Extension)

```

User
│
▼
Nexus (TUI, orchestration & governance)
│
▼
Local Server (prompts, state, streaming, ws)
│
▼
Browser Extension → ChatGPT Sessions

```

Each component has a clearly defined role.

---

## Components and Responsibilities

### User (Operator)

The user is the final authority in the system.

Responsibilities:

- Define project goals
- Approve plans and major changes
- Resolve high-impact conflicts
- Monitor progress and intervene when needed

The user interacts **only with Nexus**, not directly with sessions.

---

### Nexus

Nexus is the **orchestration and governance layer**.

Core responsibilities:

- Maintain persistent project state
- Create and evolve plans
- Break work into tasks
- Assign tasks and roles to sessions
- Evaluate reports
- Resolve conflicts
- Decide next actions
- Pause for user approval when required

Key characteristics:

- Runs locally as a TUI application
- Uses a flagship model (e.g. ChatGPT, Gemini) for reasoning
- Does **not** communicate with ChatGPT directly
- Treats sessions as ephemeral workers

Nexus is the only component that “understands” the project as a whole.

---

### Local Server

The local server acts as the **execution and communication layer**.

Responsibilities:

- Serve and process prompt files
- Manage file inclusion and prompt composition
- Stream responses from ChatGPT sessions
- Provide WebSocket communication
- Maintain per-session routing

The server is intentionally lightweight and stateless with respect to long-term project goals.

Nexus communicates with the server using:

- HTTP APIs
- WebSocket channels

---

### Browser Extension

The browser extension is the **UI integration layer**.

Responsibilities:

- Inject UI into the ChatGPT interface
- Observe user and assistant messages
- Inject prompts generated by Nexus
- Capture responses from ChatGPT sessions
- Forward structured data to the server

The extension has:

- No build step
- Minimal logic
- No long-term memory

It acts as a controlled bridge between Nexus and ChatGPT.

---

### ChatGPT Sessions

ChatGPT sessions are **ephemeral execution units**.

Characteristics:

- Each session has a specific role and task
- Sessions can run in parallel
- Sessions have no shared memory
- Sessions do not persist across Nexus restarts

From Nexus’s perspective, sessions are interchangeable workers.

---

## Control Flow

A typical control flow looks like this:

1. User defines or approves a goal
2. Nexus produces or updates a plan
3. Nexus creates one or more tasks
4. Nexus assigns tasks to sessions with roles
5. Server + extension execute prompts
6. Sessions produce structured reports
7. Nexus evaluates reports
8. Nexus decides next steps or escalates to the user

This loop continues until the project reaches a stopping point.

---

## Data Flow

### Persistent Data

Stored and managed by Nexus:

- Project goals
- Plans
- Notes
- Decisions
- Task history

### Ephemeral Data

Exists only during execution:

- ChatGPT conversations
- Live session context
- In-progress responses

This separation is intentional and central to Nexus’s design.

---

## Trust and Authority Boundaries

- ChatGPT sessions are **untrusted executors**
- Nexus is the **single source of truth**
- The user is the **final authority**

No session output is accepted blindly.  
All outputs are interpreted through Nexus’s governance logic.

---

## Failure Containment

The architecture is designed so that failures are isolated:

- A single session can fail without corrupting project state
- Sessions can be killed and restarted freely
- Nexus can reassign tasks or replan without loss of context
- Restarts do not resurrect old conversations unintentionally

This makes long-running projects safer and more predictable.

---

## Summary

In short:

- Nexus decides _what_ to do and _why_
- The server and extension handle _how_ to talk to ChatGPT
- Sessions do the work, then disappear
- The user remains in control

This architecture prioritizes governance, clarity, and long-term usability over raw automation.
